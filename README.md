# dotfiles

My personal Mac setup, managed with nix-darwin and home-manager.
One repo, one command, and this Mac ends up configured the same way every time.

Modeled on [kunchenguid/dotfiles](https://github.com/kunchenguid/dotfiles); see
[Deviations from the reference](#deviations-from-the-reference) for what's different and why.

## What you get

Running the switch builds:

- Homebrew apps: this machine's existing formulae (unchanged), plus WezTerm, herdr, and the Pi coding
  agent
- Nix user packages (ripgrep, fd, fzf, jq, lazygit, Neovim, Hack Nerd Font)
- Shell (zsh + oh-my-zsh, `robbyrussell` theme, `git` plugin, existing aliases)
- Editor (fresh Neovim config: lazy.nvim, treesitter, telescope, neo-tree, gitsigns, tokyonight)
- Terminal (WezTerm config, tokyonight color scheme, dimmed unfocused panes)
- `~/.gitconfig`, `~/.vimrc`, `~/.tmux.conf` carried over unchanged from this machine

## Prerequisites

- Apple Silicon Mac, by default.
- Intel Mac: change one line.
  In `configuration.nix`, set `nixpkgs.hostPlatform = "x86_64-darwin";` (the comment right there tells you the same thing).

## Fresh-machine setup

From a bare clone of this repo:

```sh
git clone <this-repo-url>
cd dotfiles
```

Before you run it: review "Make it yours" below, especially the Homebrew list and the
`home-manager.backupFileExtension` note if this machine already has real dotfiles on it.

```sh
./bootstrap.sh
```

`bootstrap.sh` does four things, in order:

1. Installs Determinate Nix, if it isn't already installed.
2. Symlinks this repo to `~/.dotfiles`.
   This has to happen before the first build, because `home.nix` points at config files through `~/.dotfiles`.
3. Checks the `user` configured in `flake.nix` against your actual macOS username, and offers to fix it for you if they differ.
4. Runs the first `darwin-rebuild switch`.
   It fetches the `darwin-rebuild` tool from the nix-darwin 26.05 release branch, then applies this repo's locked flake config.

After that, `darwin-rebuild` exists and you're on the normal workflow below.

### Validate without applying

Once Nix is installed (`bootstrap.sh` step 1 handles that), you can check that the config builds without touching your system:

```sh
nix flake check --no-build
nix build .#darwinConfigurations.mac.system --dry-run
```

## Daily use

Edit the config files in place, then apply:

```sh
./rebuild.sh
```

## Make it yours

- **Username**: `./bootstrap.sh` detects your macOS username and offers to set it, or change the single
  `user = "toy"` line in `flake.nix` yourself.
- **Host label** `"mac"`, in three places: `flake.nix` (the `darwinConfigurations."mac"` name),
  `rebuild.sh` (the `#mac` at the end of the flake reference), and `bootstrap.sh`'s first-switch command
  (also `#mac`). All three have to match.
- **CPU architecture**: `hostPlatform` in `configuration.nix` (see Prerequisites above).

**Homebrew cleanup:** this config does *not* set `homebrew.onActivation.cleanup`, so switching never
removes anything from Homebrew that isn't declared in `configuration.nix`'s `brews`/`casks` lists — it
only adds. If you want unlisted packages actively removed on every switch, add
`onActivation.cleanup = "zap";` under `homebrew` in `configuration.nix`, but first make sure every
package you want to keep is actually listed there.

## Repo tour

- `flake.nix` - the entry point. Wires up nixpkgs, nix-darwin, home-manager, and nix-homebrew, and
  declares the `mac` machine.
- `configuration.nix` - system-level config: Homebrew brews/casks. (No `system.defaults` - see
  Deviations below.)
- `home.nix` - user-level config: shell, packages, and the symlinks described below.
- `rebuild.sh` - re-applies the config after the first switch. Run this every time you make a change.
- `home/` - the actual config files that get symlinked into place.

## How the symlinks work

The files under `home/` are the real files - editing them here is editing your live config, no rebuild
needed to see the change in your editor. `home.nix` uses `mkOutOfStoreSymlink` to point paths like
`~/.config/nvim` straight at `home/.config/nvim` in this repo, so the two never drift out of sync.
You only run `./rebuild.sh` when you change something that isn't just a symlinked file, like the package
list.

`~/.zshrc` is generated by home-manager from `programs.zsh` in `home.nix` rather than symlinked, so edit
the shell config there, not as a standalone file.

## Deviations from the reference

This repo is modeled on [kunchenguid/dotfiles](https://github.com/kunchenguid/dotfiles) but deliberately
differs from it in a few places, because this was built to migrate an already-configured machine rather
than set up a fresh opinionated one:

1. **No `homebrew.onActivation.cleanup = "zap"`.** The reference removes any unlisted brew
   package/cask on every switch. Since this migrated a machine with real existing state, that's left
   off by default - see "Make it yours" above for how to turn it on later.
2. **No `system.defaults` block.** The reference forces its author's personal macOS UI prefs (dark
   mode, auto-hidden menu bar, Finder view style, etc.). This repo leaves current system UI behavior
   alone; add entries here if you want Nix to manage them.
3. **`home-manager.backupFileExtension = "hm-backup"`** is set in `flake.nix`. The reference doesn't
   need this because it targets fresh machines. This machine already had a plain `~/.zshrc`,
   `~/.gitconfig`, `~/.vimrc`, and `~/.tmux.conf`; without this setting the first switch fails instead
   of adopting them. With it, home-manager renames each pre-existing file to `<name>.hm-backup` before
   symlinking its own.
4. **No opinionated `~/.pi/agent` or `~/.config/herdr` content.** The reference pins two specific
   third-party Pi npm packages and ships a personal theme/extension - that's the original author's own
   audited choice, not something to carry over blind. `pi-coding-agent` and `herdr` are installed here,
   but their runtime config is left to their own defaults on first run, aside from a small
   `home/.config/herdr/config.toml` with keybindings that match this repo's tmux prefix.
5. **No Claude/Codex/opencode `AGENTS.md` symlinks, no `~/.claude/settings.json` management.** Out of
   scope for this repo; those are managed separately.
6. **Neovim config is authored fresh** for this repo (lazy.nvim, treesitter, telescope, neo-tree,
   gitsigns, tokyonight) rather than copied from the reference.

## Notes

The first time you launch `nvim`, it bootstraps [lazy.nvim](https://github.com/folke/lazy.nvim) by
cloning plugins from GitHub. That needs network access once; after that it's offline.
